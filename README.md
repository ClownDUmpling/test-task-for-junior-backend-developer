# Task Service

Сервис для управления задачами с HTTP API на Go.

## Требования

- Go `1.23+`
- Docker и Docker Compose

## Быстрый запуск через Docker Compose

```bash
docker compose up --build
```

После запуска сервис будет доступен по адресу `http://localhost:8080`.

Если `postgres` уже запускался ранее со старой схемой, пересоздай volume:

```bash
docker compose down -v
docker compose up --build
```

Причина в том, что SQL-файл из `migrations/0001_create_tasks.up.sql` монтируется в `docker-entrypoint-initdb.d` и применяется только при инициализации пустого data volume.

## Swagger

Swagger UI:

```text
http://localhost:8080/swagger/
```

OpenAPI JSON:

```text
http://localhost:8080/swagger/openapi.json
```

## API

Базовый префикс API:

```text
/api/v1
```

Основные маршруты:

- `POST /api/v1/tasks`
- `GET /api/v1/tasks`
- `GET /api/v1/tasks/{id}`
- `PUT /api/v1/tasks/{id}`
- `DELETE /api/v1/tasks/{id}`

## Реализация периодичности задач

### Подход

Периодичность задаётся прямо при создании задачи через опциональное поле `recurrence`. Если поле не передано — задача одноразовая. Если передано — задача становится шаблоном.

Из шаблонов планировщик автоматически создаёт экземпляры задач каждую минуту. Каждый экземпляр хранит `parent_id` (ссылка на шаблон) и `scheduled_date` (дата на которую создан).

### Типы периодичности

- `daily` — каждые N дней. Требует поле `every_n_days` (целое число больше 0). Отсчёт ведётся от даты создания шаблона.
- `monthly` — в определённые числа месяца. Требует поле `month_days` (массив чисел от 1 до 30).
- `specific_dates` — на конкретные даты. Требует поле `dates` (массив дат в формате RFC3339).
- `even_odd` — по чётным или нечётным дням месяца. Требует поле `parity` со значением `even` или `odd`.

### Пример создания периодической задачи

```json
POST /api/v1/tasks
{
  "title": "Обзвон пациентов",
  "description": "Ежедневный обзвон",
  "status": "new",
  "recurrence": {
    "type": "daily",
    "every_n_days": 1
  }
}
```

### Принятые решения

**Один эндпоинт вместо двух.** Периодичность добавлена в существующий `POST /api/v1/tasks` как опциональное поле, а не через отдельный эндпоинт для шаблонов. Это сохраняет простоту API и не требует от клиента знать о внутреннем разделении на шаблоны и экземпляры.

**Одна таблица вместо двух.** Шаблоны и экземпляры хранятся в одной таблице `tasks`. Шаблон — задача с заполненным `recurrence_type` и пустым `parent_id`. Экземпляр — задача с заполненным `parent_id` и пустым `recurrence_type`. Это упрощает схему БД и репозиторий.

**Планировщик запускается раз в минуту.** Достаточная точность для задач с дневной периодичностью. При старте сервиса планировщик сразу проверяет нужно ли создать задачи на сегодня — на случай если сервис перезапускался в течение дня.

**Защита от дублей.** Перед созданием экземпляра планировщик проверяет не существует ли уже задача с таким `parent_id` и `scheduled_date`. Повторного создания не будет даже если сервис перезапускался несколько раз за день.

**Каскадное удаление.** При удалении шаблона все его экземпляры удаляются автоматически через `ON DELETE CASCADE`.

**Числа месяца до 30.** Для типа `monthly` допустимы числа от 1 до 30. Число 31 намеренно исключено — не все месяцы имеют 31 день, что могло бы приводить к пропускам задач.
